# 测试监控体系三层设计与运动科技引入决策

## R — 原文 (Reading)

> "A decision-making framework for implementing technology in sport suggests four reflective questions: 1. Would the information provided be helpful? 2. Can you trust the information provided? 3. Can you integrate, manage, and analyze the data provided effectively? 4. Can you implement the technology in your practice?"

— Chapter 14 · Administration (technology in sport)（`ch14.txt:358-361`）

## I — 自述 (Interpretation)

把测试监控体系组织成**三层嵌套**，上定框架、中定步骤、下选工具：

1. **Protocol（协议）**：总体策略——测什么能力、整个赛季的测试类型与频率。
2. **Procedure（程序）**：协议框架内的逐步执行细则，保证一致、可靠、有效地采集数据。
3. **Equipment（器材）**：在众多可选设备中挑选，须过效度/信度、实用性/易用性、与运动员及专项的相关性。

引入新科技（力台、IMU、手机 App、AI 分析）时用**四问闸门**筛：
1. 该信息**有用**吗？
2. 该信息**可信**吗（设备效度/信度）？
3. 能否有效**整合、管理、分析**数据？
4. 能否在实践中**落地**？

只有四问都过，引入才既准确又可行、既相关又可执行。测试开始前须审查三层；并定期复核，使电池保持一致、相关、有效。

## A1 — 案例 / 演练 (Application)

**原书未提供完整案例**，只给四问框架与三层结构（`f14-01`、`f14-02`；`p14-58`）。

**合成演练（明确标记）**：拟引入某手机 App 测量纵跳（用高速摄像估算腾空时间）。
- 四问逐一判定：信息有用（是）→ 可信（需核效度/信度）→ 能否整合（需能导出数据）→ 能否落地（队内能否人人用）。
- 结论：输出"先做与力台/接触垫的一致性验证，再采用"的引入闸门结论与所需验证动作。

## A2 — 未来触发 (Trigger)

**用户情境**：
1. 想引入某个新设备/App/软件来做测试，问"值不值得上"。
2. 要设计一套赛季监控体系，问"协议、程序、器材怎么分层"。
3. 器材很多不知怎么选，怕买到不靠谱的。
4. 要定期复核现有测试电池是否仍一致、相关、有效。

**语言信号（中英双写）**：运动科技 / 引入设备 / 监控体系 / 协议 / 器材选型 / technology / monitoring protocol / equipment selection / VBT device / 该不该买这个设备 / data integration / 复核测试电池。

**与相邻能力的区分**：本卡管"体系与工具引入决策"；具体测试的协议在 `max-strength-test-protocols` 等族卡；测试顺序与休息归 `test-sequencing-rest`。

## E — 执行 (Execution)

**输入契约**：赛季目标 + 要监控的身体能力 + 候选器材/技术清单 + 队内资源（人、时间、软件）。缺目标无法定协议。

**步骤与完成标准**：
1. **定 Protocol**：写明测什么能力、整个赛季的测试类型与频率。完成标准：一页纸协议（能力清单 + 频率表）。
2. **写 Procedures**：为每项测试写逐步执行细则，保证一致采集。完成标准：步骤可被他人照做。
3. **选 Equipment**：对候选器材逐项过"效度/信度、实用/易用、相关性"。完成标准：每项给"采用/不采用 + 理由"。
4. **过四问闸门**（仅针对新技术/工具）：有用→可信→可整合分析→可落地。完成标准：四问逐条判定，全过才引入。
5. **前置验证**：若可信度未知，先做与既有金标准的一致性验证。完成标准：写明验证方案与通过标准。
6. **定期复核**：设定复核周期，保持电池一致、相关、有效。完成标准：写明复核间隔。
7. **输出**。

**输出契约**：`{protocol(能力+频率), procedures(逐步), equipment选型表, 四问判定结果, 引入/否决结论, 前置验证方案, 复核周期}`。

**判停点/分支**：
- 四问中任一问不通过（尤其"可信"未验证）→ 不引入，先验证。
- 已在用的测试与新工具冲突 → 先做一致性验证再决定替换。

**约定**：原文四问均为**定性提问，未给量化判据或通过阈值**（`f14-01` gap）。本卡要求逐条写明判定与证据，标为约定，不虚构评分。

## B — 边界 (Boundary)

- **不要**因"新、酷、数据多"就引入工具；先过四问。
- **不要**跳过效度/信度验证直接采用新设备数据做决策。
- **作者盲点（3.1 数字化工具快速过时）**：书中对 GPS/VBT/AI 着墨偏辅助，工具生态迭代快，本卡给的是决策框架而非具体工具推荐。
- **共识 ≠ 实证**：四问是启发式闸门，非量化标准。
- **专业边界（2.2-14）**：数据解读不等于医疗/营养建议，越界处置需转诊。
- **相邻易混**：与具体测试协议族卡不同——本卡是"体系与工具层"。
